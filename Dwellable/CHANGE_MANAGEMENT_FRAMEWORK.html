🔧 Change Management Framework

Ensure every code change is safe, consistent, and doesn't break existing flows

Welcome to the Change Management Framework

Purpose: Ensure every code change is safe, consistent, and doesn't break existing flows.
When to use: Before committing ANY feature, bug fix, or refactor.

The Core Problem We're Solving

You make a small change to one file, but it breaks another file that depends on it. Or you update the same concept in one place but forget to update it in another place where it also appears. The framework prevents this.

The 4-Step Safety System

Step What Why Time
1 Impact Analysis Identify all files and concepts affected before coding 5 min
2 Consistency Check Find all places a concept appears, ensure all are updated 5 min
3 Manual Testing Run 7 Critical Path tests on real device (regression prevention) 30 min
4 Code Review Walk through pre-commit checklist before committing 5 min
✅ Total time per commit: 45 minutes for bug fix, 1-2 hours for small feature

⚙️ The Workflow

Before Every Commit

Step 1: Write code → Make your change → Compile (Xcode) → No warnings/errors? Step 2: Impact analysis (5 min) → What files changed? → What concepts affected? → What flows impacted? → Create impact map Step 3: Consistency check (5 min) → Does this pattern appear elsewhere? → Are all instances updated? → Complete consistency checklist Step 4: Manual testing (30 min) → Build on device → Run Critical Path tests (all 7 journeys) → All pass? Step 5: Code review checklist (5 min) → Walk through pre-submission checklist → Everything checked? Step 6: Commit → Good commit message (WHAT + WHY) → Push to branch → Create PR if needed Step 7: Merge → All tests pass → Code review complete → No outstanding issues → Merge to main

Critical Path Tests (7 Journeys)

These are the MINIMUM tests that MUST PASS before any commit.

✓ Journey 1: Capture → Review → Save → View ▼

Steps:

  1. Open app → Login
  2. Tap record button
  3. Speak for 5 seconds
  4. Review transcript (verify no blank state)
  5. Tap Save
  6. Moment appears in list
  7. Tap moment → view detail

If any step fails: DO NOT COMMIT

✓ Journey 2: Offline Capture → Sync ▼
  1. Disable WiFi/Cellular (Airplane mode)
  2. Record 5 seconds
  3. Save moment
  4. Verify moment in list (offline)
  5. Enable network
  6. Verify moment syncs (check list updates)

If any step fails: DO NOT COMMIT

✓ Journey 3: 10-Minute Recording ▼
  1. Start recording (tap record)
  2. Record continuously for 10 minutes
  3. Verify warning appears at 9:00 ("60 seconds left")
  4. Verify recording auto-stops at 10:00
  5. Review transcript
  6. Save moment

If any step fails: DO NOT COMMIT

✓ Journey 4: Transcription Error → Retry ▼
  1. Record 2 seconds of silence
  2. Verify error message (not blank moment)
  3. Tap "Retry Transcription"
  4. Record valid audio
  5. Verify transcription completes
  6. Save moment

If any step fails: DO NOT COMMIT

✓ Journey 5: App Backgrounding ▼
  1. Start recording
  2. Record 3 seconds
  3. Background app (home button)
  4. Verify recording stopped
  5. Reopen app
  6. Verify you're back at home screen (not ReviewView)

If any step fails: DO NOT COMMIT

✓ Journey 6: Sync Queue Recovery ▼
  1. Save moment while offline
  2. Force-quit app (swipe from recents)
  3. Reopen app
  4. Verify moment still there
  5. Enable network
  6. Verify moment syncs

If any step fails: DO NOT COMMIT

✓ Journey 7: Text Entry ▼
  1. Tap "Type" tab in Capture
  2. Enter 200+ words
  3. Save moment
  4. Verify appears in list
  5. Tap moment → view detail
  6. Verify full text displays

If any step fails: DO NOT COMMIT

🎯 Impact Analysis

Before Writing Code, Answer These Questions

Question 1: What files will this change touch?

Example: Fixing [BLANK_AUDIO] stripping

Files affected: - TranscriptionManager.swift (core change) - ReviewView.swift (uses transcript) - XCUI tests for transcription (test file)

Question 2: What concepts/patterns appear in multiple places?

Example: The concept of "transcript validation" appears in:

1. TranscriptionManager.transcribeAudio() — strips [BLANK_AUDIO] 2. ReviewView — shows loading spinner while momentBody empty 3. APIClient.saveMoment() — validates non-empty body before API call If you change #1, you must verify #2 and #3 still work.

Question 3: What other screens depend on this data?

Example: If you change how audio is stored:

- ReviewView displays audio (don't break) - MomentDetailView plays audio (don't break) - MomentsListView shows audio indicators (don't break) - SyncManager queues audio uploads (don't break) Each must be tested.

Create an Impact Map

Before starting, fill in this template:

## Change: [Describe the change] **Files modified:** - [ ] File A (line X-Y) - [ ] File B (line X-Y) **Concepts affected:** - [ ] Concept 1 (appears in: Screen A, Manager B, API C) - [ ] Concept 2 (appears in: Screen D, Test E) **User flows impacted:** - [ ] Capture + Review + Save - [ ] Offline save + Sync + List - [ ] View moment + Edit + Save - [ ] (others) **Tests that MUST pass:** - [ ] Critical Path tests (see section 4) - [ ] Tests for affected concepts

🔄 Consistency Checking

When a Concept Appears in Multiple Places

Ensure all instances are updated together.

Example: Recording Duration Limits

Pattern: "10-minute recording with 9-minute warning"

Where this appears:

Location Component Check
1 CaptureView Shows 9:00 warning (gold message)
2 AudioRecordingManager Auto-stops at 10:00
3 Timer logic Calculates remaining time
4 Tests Verify warning + auto-stop
5 Docs Documented in CLAUDE.md
6 UI text Consistent phrasing ("60 seconds left")
If you change #1 (warning text), verify:
☐ All 6 instances still work together
☐ Tests still pass
☐ User sees consistent UX across all screens

✅ Testing & Automated Tests

What I CAN Test (10-15 tests)

Pure Logic Unit Tests (5-8 tests):
• String cleaning ([BLANK_AUDIO] stripping)
• Transcript validation (empty detection, edge cases)
• Text normalization (UTF-8, emoji preservation)
• Timestamp calculations (timer logic)
• Data transformation (model mapping)
Schema Verification Tests (3-5 tests):
• Tables exist in database
• Columns correct type/nullable
• RLS policies in place
• Indexes created
• Foreign keys defined
API Contract Tests (2-3 tests):
• Request format correct (mocked)
• Response parsing works
• Error handling (mocked failures)

What I CANNOT Test

❌ Integration Tests — Would pollute your production database
Real API calls create test data, side effects can't be cleaned up
❌ Real Network Tests — Would waste storage & create orphaned data
Audio upload tests create files in your Storage
❌ Audio/Transcription Tests — No hardware access
Can't access device microphone or run WhisperKit ML model
❌ UI/XCUI Tests — Flaky and unreliable on simulator
Simulator crashes after 60 seconds, tests are slow and timing-dependent
❌ Device-Specific Tests — Can't control iOS lifecycle
Can't toggle airplane mode, trigger low battery, or measure real battery drain

The Real Testing Split

What I Write What You Write
~15 unit tests (pure logic, no side effects) 7 Critical Path tests (regression prevention, 30 min)
Catches: obvious bugs, edge cases, data transformation errors 57 Comprehensive scenarios (feature validation, 4-5 hours)
Catches: UX issues, device-specific bugs, real-world edge cases, performance problems
Why this ratio: The app's value is in audio, transcription, sync, and UX. These require real device interaction and human validation. Unit tests are supporting roles, not the main story.

📝 Pre-Commit Checklist

Before Every Commit, Check These Boxes

CODE QUALITY

  • Builds successfully (no errors/warnings)
  • No debug code or console logs
  • No commented-out code
  • No force-unwrapping (use guard/if-let)
  • Error handling present
  • No hardcoded strings (use constants)

TESTING

  • Impact map completed
  • Consistency checklist completed
  • Critical Path tests: ALL 7 PASS
  • Automated tests: ALL PASS (if written)
  • Tested on DEVICE (not simulator)
  • Tested in different conditions (WiFi, cellular, offline)

CONSISTENCY

  • If UI changed: All screens using same component verified
  • If logic changed: All call sites verified
  • If API changed: All call sites updated
  • If database changed: Schema + migrations correct
  • Patterns updated everywhere

DOCUMENTATION

  • CLAUDE.md updated (if needed)
  • Code comments added (if non-obvious)
  • Commit message includes WHAT + WHY

Commit Message Format

[Type]: [What changed] [Why this change] [What was tested] [Any caveats/notes] Example: Fix: Strip [BLANK_AUDIO] marker from transcripts Prevents garbled [BLANK_AUDIO] text from being saved as moments. User was seeing "moment saved" but actual text was corrupted. Testing: Critical Path tests 1-7 pass. Verified: - Silence still rejected with error message - Valid speech captured correctly - No regressions in TranscriptionManager Docs: Updated CLAUDE.md with known limitation.

Emergency Decision Tree

Q: One of the 7 Critical Path tests FAILED. What do I do? ▼

A: STOP. DO NOT COMMIT.

  • Understand why it failed
  • Fix the code
  • Re-run all 7 tests
  • Only commit when ALL pass
Q: I found a bug in an unrelated area while testing. Can I fix it? ▼

A: Create a SEPARATE commit for it.

  • Finish the current change
  • Commit the current change (if tests pass)
  • Then create a NEW branch for the bug fix
  • Test and commit that separately
Q: How long should this whole process take? ▼

A: Depends on change type:

  • 30-45 min for small bug fix
  • 1-2 hours for small feature
  • 3-5 hours for medium feature
  • 5+ hours for large feature / architectural change
