📖 Terminology (Locked)
Stewarding — the umbrella entry act
  • Capturing a moment (no prompt engagement) — the user is "stewarding" what's on their heart but not yet going deeper.
Dwelling — three forms, ranked from deepest to lightest
  1. Praying on a captured moment — highest form of dwelling
  2. Capturing + responding to prompts — 2nd highest form (capture deepened by prompt engagement)
  3. Editing a journal entry — 3rd highest form

Retired terms: "Soaking" (use "dwelling"). Parked: "Reflecting vs Dwelling" relationship — revisit later.

⚠️ Important Scope Clarification: This taxonomy describes product-level user-action precedence (which acts count as deeper engagement). It does NOT route notifications. Specifically: prompt response is form #2 dwelling for product purposes, but has zero influence on notification timing, copy, or routing. Whether a user responded to prompts or not, the notification engine treats them the same. The stage table below reflects only notification-relevant signals (capture, prayer, journal return).
📌 Cross-Pillar Requirements (Flow Back to Other Pillars) This notification strategy depends on these requirements being locked into other pillars. They surfaced during this strategy work and need to be formalized:
  • Pillar 0 (Onboarding): Must mandate first capture before app navigation. User cannot bypass capture to access broader app features. Without this, Stage B's "push only / no in-app parity" assumption breaks. ✓ FILED INTO PILLAR 0 STRATEGY DOC
  • Pillar 4 (Journal): Journal entries can only exist as AI synthesis from prayer. No standalone journal creation. This is why C2 (journaled-without-prayer) was removed — logically impossible.
  • Pillar 0 (Onboarding) — Screen 6.5 Notification Permission: Standalone screen between Privacy (Screen 6) and First Capture (Screen 7). Opt-out model; if user declines, no notifications fire ever (Pillar 8 engine respects OS permission flag). ✓ FILED INTO PILLAR 0 STRATEGY DOC
  • T-086 (Settings UI): Three notification modes — Default (all stage rules apply), Sparse (caps everything to 1x/month, suppresses F/G entirely), Off (push disabled; in-app stays). Add Sabbath / Quiet Days toggle for users observing a rest day.
⏱ 7-Day Funnel Window (Design Philosophy) A dweller can complete the full funnel — capture → prayer → journal return — within ~3 days if they engage with each notification. The 7-day window is the buffer.
  • Day 1: Stage B push fires → user captures.
  • Day 2 (~12h after capture): Stage C push fires → user prays.
  • Day 3 (8am after prayer): Stage D push fires → user returns to journal.
  • Day 7: If user is still in B/C/D, soft-escalate or pause — respect their pace.
This window is a Pillar 0/1 design principle. The stage table below enforces it through cool-off windows aligned with the 7-day frame.
🟢 Channel Strategy — Mutually-Suppressive Parity (Global Rule) When a stage has both push + in-app variants, they operate as mutually suppressive. Each push has three possible user outcomes, each with a distinct consequence:
📲 Tap
App opens to the intended action. If user completes the action → cycle ends. If user exits without acting → in-app remains suppressed for 24h; next push fires per cool-off.
✗ Dismiss
User actively swipes/clears push. In-app surfaces on next organic app open within 24h.
⌖ Ignore
Push neither tapped nor dismissed (sits unread). In-app surfaces on next organic open within 7d window.
Two additional global rules:
  • User acts on in-app first (before push fires) → next scheduled push for that cycle is suppressed.
  • 24h with no engagement on either surface → both expire; new cycle starts at next interval.

💡 Practical Example — "Combined Cap" in Action
Maria — healthy F/G dweller:
  • Mon: Maria captures a moment.
  • Tue 7am: F push fires → "How is that moment sitting with you?"
  • Tue evening: Maria taps push, prays. User transitions F → G.
  • Wed 7am: G push would normally fire... BUT it's suppressed because F already fired this calendar week.
  • Next Mon: G can now fire (new week).
Net effect: healthy alternating dwellers see at most 1 push/week, often 0 (if they're alternating organically without prompts). This is a ceiling, not a baseline.
