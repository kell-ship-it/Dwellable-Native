Notifications Strategy

Pillar 8 · May 6, 2026 · Strategy Locked
0 comments

1. Overview

Pillar: 8 (Notifications & Nudges)
Purpose: Drive user return and deeper dwelling engagement through sparse, contextual invitations to dwell
Scope: Push notifications + in-app notifications (MVP); no email
Status: Strategy locked, ready for implementation
Philosophy: "Invitations to dwell," not "reminders to use the app"

2. Product Purpose

The Problem Notifications Solve

  • Phase 1 validation: 100% capture adoption, 0% return rate
  • Root cause: Users aren't returning to reflect on moments they captured
  • Solution: Sparse, meaningful notifications that invite users back to dwell on their moments

Why Pillar 8 (Last)

  • Notifications only work after there are compelling experiences (Prayer/Dwelling from Pillar 3)
  • Without good prayer prompts, notifications just nag users to use an empty app
  • Pillar 5 (Search) makes moments accessible; Pillar 8 invites users back to them

3. Success Criteria

Qualitative

  • Notifications feel like invitations, not reminders
  • Users perceive notifications as genuinely helpful, not pushy
  • Notifications respect the spiritual/faith tone of Dwellable (not productivity-gamified)

Quantitative

  • D7 Retention increases to >35% (from 0% baseline)
  • Formation Engagement Rate (% of users dwelling) increases >20% (MVP: dwelling = prayer on a captured moment OR journal return — prompt response not counted)
  • Click-through rate on notifications >40% (users act on invitations)
  • Opt-out rate <10% (users keep notifications enabled)
  • No increase in churn from notification fatigue

5. Funnel Stages — Notification Playbook

We segment by where someone is in the funnel — not by who we think they are. Archetypes are Post-MVP.

Funnel: Onboarded → Captures → Responds to Prompt → Prays → Returns to Journal → Consistent Dwelling

Dwelling (MVP) = praying on a captured moment OR returning to a journal entry (to edit, add context, or pray/journal from a notification). Responding to a prompt is not counted as dwelling — it's a positive signal that reduces notification urgency but does not advance funnel stage. A user's funnel stage is determined by the deepest dwelling act they've taken.

Each stage below specifies: Condition (who this applies to), Why (intervention goal), When to fire (timing trigger), and Cool-off (suppression rules) — followed by Push and In-App message options.

Dormancy Reset Rule

Any user who reaches Stage D (actively dwelling) and then goes quiet for 14+ consecutive days is automatically routed to Stage C3 notification logic. No penalty framing — the same gentle re-invite applies regardless of how active they were before.

The transition is invisible to the user. Functionally: Stage D check runs daily; if last dwelling act is 14+ days ago, switch to C3 rules. Escalation follows normal C3 cool-off from that point.

Global Frequency Caps

  • Push: Max 1–2 per user per month across all stages — exception: B1/B2 operate on weekly cadence (prayer is time-sensitive; caps don't override active discovery stages)
  • In-App: 1 active nudge visible at a time; no stacking; dismiss on action

Optimal Push Send Time

  • Primary: User's typical app-open time (inferred from usage data)
  • Fallback: 9am local time if usage pattern is unclear
  • Blackout: Never between 10pm–7am local time

6. Personalization Rules (Plaintext Readable, Server-Side Encryption)

NOTE: Moments are encrypted server-side (protected against external theft/breach). Dwellable can read plaintext for personalization, synthesis, and Formation Intelligence. Users trust Dwellable with their moments; encryption protects against hackers, not against Dwellable access.

What we CAN personalize

  • ✓ Timing (when user typically opens app)
  • ✓ Dwelling history (prayer vs. prompt preference)
  • ✓ Funnel stage (A–D)
  • ✓ Engagement frequency (# of moments captured, # of prayers, # of prompt responses)
  • ✓ Moment themes ("You captured about faith") — plaintext readable
  • ✓ Specific moment content (reference what user wrote) — plaintext readable

MVP Personalization Approach

  • A0–C3: Metadata + activity-type (funnel stage, engagement frequency)
  • D (MVP): Activity-type references ("that prayer," "what you've processed") — simple, low-cost
  • D (Post-MVP): Topic-aware ("You shared about faith. How's that going?") — requires plaintext processing, higher cost

Privacy Transparency

  • Moments are encrypted against external theft
  • Dwellable reads plaintext for personalization, synthesis, and Formation Intelligence
  • No third-party access (Google, OpenAI) to plaintext without explicit consent
  • Users trust Dwellable with their spiritual moments; this is the design choice that honors that trust

8. Privacy & Server-Side Encryption

Privacy Promise (revised):

"Your responses are encrypted. Only you and Dwellable can see your moments. We protect them from hackers and external theft."

Notification Transparency

  • MVP: Notifications reference activity type (prayer, processing) and engagement patterns
  • Post-MVP: Notifications reference themes and content from plaintext (e.g., "You shared about faith")
  • All personalization happens server-side with plaintext access
  • No third-party access to plaintext (Google, OpenAI) without explicit user consent
  • Users can disable notifications entirely in settings

Trust Model

User research from Phase 1 beta: Users care more about "Kell won't read my diary" than "OpenAI won't read my diary." Encryption protects against external theft; privacy promise reflects that we honor their trust by not exposing moments to third parties without consent.

Worst-Case Concurrent Notifications

  • Per single user: 1 push per weekly send window (e.g., Thursday 8am). No stacking — if user misses a push, next push replaces it.
  • Global (at 10K users): Estimated 1K–2K concurrent pushes on any given day (out of 10K total users, ~20% in active notification-eligible stages). FCM queue handles this without issue.
  • Global (at 100K users): Estimated 10K–20K concurrent pushes. Still well within FCM capacity (handles millions/day).

Bottleneck is not cost; it's ensuring notifications drive measurable retention impact. See Section 16 (Tests) for measurement plan.

12. Implementation Approach

Phase 1: Infrastructure (Weeks 1–2)

  • Set up push notification service (Firebase Cloud Messaging for iOS)
  • Build notification scheduling system
  • Implement opt-out/settings UI
  • Add analytics event logging

Phase 2: User Segmentation (Weeks 2–3)

  • Build logic to identify funnel stage (A, B1, B2, C, D) per user
  • Store segment assignment in database

Phase 3: Generic Notifications (Weeks 3–4)

  • Write generic notification templates for each segment
  • Test delivery, timing, click behavior
  • Measure baseline CTR and conversion

Phase 4: Timing Optimization (Weeks 5+)

  • Analyze when users typically open app
  • Schedule notifications for optimal time
  • A/B test: fixed time vs. smart time

16. Open Questions (To Resolve Before Tickets)

  1. Should we launch Pillar 8 with generic notifications only, or wait for better personalization?
    — Decision: Ship generic first (Phases 1–3), validate if notifications drive return at all
  2. How do we handle users who never engage with notifications?
    — Strategy: After 3 consecutive "no clicks," soft pause for 2 weeks, then retry
  3. Should onboarding explain why they're receiving notifications?
    — Recommendation: Yes, brief tooltip explaining Pillar 8 purpose
  4. Should notification frequency be user-configurable?
    — Recommendation: Yes, in Settings (weekly, bi-weekly, monthly options)
