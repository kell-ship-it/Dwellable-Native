Notifications Strategy

Pillar 8 · May 6, 2026 · Strategy Locked
0 comments

1. Overview

Pillar: 8 (Notifications & Nudges)
Purpose: Drive user return and deeper dwelling engagement through sparse, contextual invitations to dwell
Scope: Push notifications + in-app notifications (MVP); no email
Status: Strategy locked, ready for implementation
Philosophy: "Invitations to dwell," not "reminders to use the app"

2. Product Purpose

The Problem Notifications Solve

  • Phase 1 validation: 100% capture adoption, 0% return rate
  • Root cause: Users aren't returning to reflect on moments they captured
  • Solution: Sparse, meaningful notifications that invite users back to dwell on their moments

Why Pillar 8 (Last)

  • Notifications only work after there are compelling experiences (Prayer/Dwelling from Pillar 3)
  • Without good prayer prompts, notifications just nag users to use an empty app
  • Pillar 5 (Search) makes moments accessible; Pillar 8 invites users back to them

3. Success Criteria

Qualitative

  • Notifications feel like invitations, not reminders
  • Users perceive notifications as genuinely helpful, not pushy
  • Notifications respect the spiritual/faith tone of Dwellable (not productivity-gamified)

Quantitative

  • D7 Retention increases to >35% (from 0% baseline)
  • Formation Engagement Rate (% of users dwelling) increases >20% (MVP: dwelling = prayer on a captured moment OR journal return — prompt response not counted)
  • Click-through rate on notifications >40% (users act on invitations)
  • Opt-out rate <10% (users keep notifications enabled)
  • No increase in churn from notification fatigue

📖 Terminology (Locked)
Stewarding — the umbrella entry act
  • Capturing a moment (no prompt engagement) — the user is "stewarding" what's on their heart but not yet going deeper.
Dwelling — three forms, ranked from deepest to lightest
  1. Praying on a captured moment — highest form of dwelling
  2. Capturing + responding to prompts — 2nd highest form (capture deepened by prompt engagement)
  3. Editing a journal entry — 3rd highest form

Retired terms: "Soaking" (use "dwelling"). Parked: "Reflecting vs Dwelling" relationship — revisit later.

⚠️ Important Scope Clarification: This taxonomy describes product-level user-action precedence (which acts count as deeper engagement). It does NOT route notifications. Specifically: prompt response is form #2 dwelling for product purposes, but has zero influence on notification timing, copy, or routing. Whether a user responded to prompts or not, the notification engine treats them the same. The stage table below reflects only notification-relevant signals (capture, prayer, journal return).
📌 Cross-Pillar Requirements (Flow Back to Other Pillars) This notification strategy depends on these requirements being locked into other pillars. They surfaced during this strategy work and need to be formalized:
  • Pillar 0 (Onboarding): Must mandate first capture before app navigation. User cannot bypass capture to access broader app features. Without this, Stage B's "push only / no in-app parity" assumption breaks. ✓ FILED INTO PILLAR 0 STRATEGY DOC
  • Pillar 4 (Journal): Journal entries can only exist as AI synthesis from prayer. No standalone journal creation. This is why C2 (journaled-without-prayer) was removed — logically impossible.
  • Pillar 0 (Onboarding) — Screen 6.5 Notification Permission: Standalone screen between Privacy (Screen 6) and First Capture (Screen 7). Opt-out model; if user declines, no notifications fire ever (Pillar 8 engine respects OS permission flag). ✓ FILED INTO PILLAR 0 STRATEGY DOC
  • T-086 (Settings UI): Three notification modes — Default (all stage rules apply), Sparse (caps everything to 1x/month, suppresses F/G entirely), Off (push disabled; in-app stays). Add Sabbath / Quiet Days toggle for users observing a rest day.
⏱ 7-Day Funnel Window (Design Philosophy) A dweller can complete the full funnel — capture → prayer → journal return — within ~3 days if they engage with each notification. The 7-day window is the buffer.
  • Day 1: Stage B push fires → user captures.
  • Day 2 (~12h after capture): Stage C push fires → user prays.
  • Day 3 (8am after prayer): Stage D push fires → user returns to journal.
  • Day 7: If user is still in B/C/D, soft-escalate or pause — respect their pace.
This window is a Pillar 0/1 design principle. The stage table below enforces it through cool-off windows aligned with the 7-day frame.
🟢 Channel Strategy — Mutually-Suppressive Parity (Global Rule) When a stage has both push + in-app variants, they operate as mutually suppressive. Each push has three possible user outcomes, each with a distinct consequence:
📲 Tap
App opens to the intended action. If user completes the action → cycle ends. If user exits without acting → in-app remains suppressed for 24h; next push fires per cool-off.
✗ Dismiss
User actively swipes/clears push. In-app surfaces on next organic app open within 24h.
⌖ Ignore
Push neither tapped nor dismissed (sits unread). In-app surfaces on next organic open within 7d window.
Two additional global rules:
  • User acts on in-app first (before push fires) → next scheduled push for that cycle is suppressed.
  • 24h with no engagement on either surface → both expire; new cycle starts at next interval.

6. Personalization Rules (Plaintext Readable, Server-Side Encryption)

NOTE: Moments are encrypted server-side (protected against external theft/breach). Dwellable can read plaintext for personalization, synthesis, and Formation Intelligence. Users trust Dwellable with their moments; encryption protects against hackers, not against Dwellable access.

What we CAN personalize

  • ✓ Timing (universal 7am in dweller's timezone — see Section 4)
  • ✓ Dwelling history (prayer vs. prompt preference)
  • ✓ Funnel stage (A–G)
  • ✓ Engagement frequency (# of moments captured, # of prayers, # of prompt responses)
  • ✓ Moment themes ("You captured about faith") — plaintext readable
  • ✓ Specific moment content (reference what user wrote) — plaintext readable

MVP Personalization Approach

  • Stages A–D (new-user funnel): Metadata + activity-type (funnel stage, engagement frequency) — no content references
  • Stage D (MVP): Activity-type references ("that prayer," "what you've processed") — single locked copy variant; low-cost
  • Stages F/G — Post-MVP: Topic-aware ("You captured something about [theme]. Ready to bring it to prayer?") — requires plaintext processing, higher cost; locked variant ships in MVP
  • Stage E — Post-MVP alternation: If last act was capture → invite prayer; if last act was prayer → invite capture. Same 14-day cadence as MVP E, but context-aware copy.

Privacy Transparency

  • Moments are encrypted against external theft
  • Dwellable reads plaintext for personalization, synthesis, and Formation Intelligence
  • No third-party access (Google, OpenAI) to plaintext without explicit consent
  • Users trust Dwellable with their spiritual moments; this is the design choice that honors that trust

8. Privacy & Server-Side Encryption

Privacy Promise (revised):

"Your responses are encrypted. Only you and Dwellable can see your moments. We protect them from hackers and external theft."

Notification Transparency

  • MVP: Notifications reference activity type (prayer, processing) and engagement patterns
  • Post-MVP: Notifications reference themes and content from plaintext (e.g., "You shared about faith")
  • All personalization happens server-side with plaintext access
  • No third-party access to plaintext (Google, OpenAI) without explicit user consent
  • Users can disable notifications entirely in settings

Trust Model

User research from Phase 1 beta: Users care more about "Kell won't read my diary" than "OpenAI won't read my diary." Encryption protects against external theft; privacy promise reflects that we honor their trust by not exposing moments to third parties without consent.

  • A/B test: fixed time vs. smart time

16. Open Questions

Questions with ✅ are resolved and locked. Remaining open questions need resolution before ticket implementation begins.

  1. ✅ Should we launch Pillar 8 with generic notifications only, or wait for better personalization?
    Resolved: Ship locked MVP variants (generic, stage-specific copy) first. Validate that notifications drive return at all before adding personalization. Post-MVP topic-aware variants depend on LLM tournament outcome.
  2. ✅ How do we handle users who never engage with notifications?
    Resolved: Per-stage stop conditions are now locked in Section 5. Summary: most stages stop after 4 ignored cycles; Stage D is single-shot with no retry; Stage E reduces to pause after 3 consecutive ignores (42+ days). Settings manual pause always available via T-086.
  3. ✅ Should onboarding explain why they're receiving notifications?
    Resolved: Yes — Pillar 0 (Onboarding) now includes a dedicated Screen 6.5 between Privacy (Screen 6) and First Capture (Screen 7). Copy: "We'll only send sparse, gentle invitations when there's something worth coming back to." Opt-out model (default enabled). Filed into Pillar 0 strategy doc — see Cross-Pillar Requirements in Section 5.
  4. ✅ Should notification frequency be user-configurable?
    Resolved: Yes, via T-086 (Settings UI). Three modes: Default (all stage rules apply), Sparse (caps everything to 1x/month, suppresses F/G entirely), Off (push disabled; in-app contextual surfaces remain). A Sabbath / Quiet Days toggle will also be available for users observing a rest day.
  5. ⏳ LLM tournament outcome — effect on personalization depth
    — Open: Post-MVP personalization (topic-aware copy for F/G and E alternation) requires a decision on whether to use a server-side LLM (Gemini — requires carving out a readable metadata field, relaxing E2E for that field) or on-device LLM (Mistral — full E2E, richer personalization without server access). Blocked until LLM tournament results are in. MVP ships with locked generic variants regardless.
  6. ⏳ Sabbath / Quiet Days toggle — implementation scope
    — Open: T-086 (Settings UI) should include this toggle. Design decision needed: does "Quiet Day" suppress only push notifications, or also in-app contextual surfaces? And does the user set specific days, or flag an active period? Needs UX spec before T-086 begins.
