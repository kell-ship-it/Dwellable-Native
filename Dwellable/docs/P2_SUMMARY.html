Pillar 2: Security & Privacy — Skeleton Summary

What We're Building

Pillar 2 (Security & Privacy) is the encryption and key management layer that protects all captured moments. Every moment is encrypted locally before syncing to the server, ensuring user data remains private and inaccessible to Dwellable or any third party.

1
Account Creation → Key Derivation

User sets password during signup (pillar 0). Argon2id KDF derives master encryption key from password (memory-hard, salt-based). Master key stored in iOS Keychain. Password never stored locally.

2
Moment Capture → Local Encryption

Moment captured, transcribed/typed, and auto-headline generated (pillar 1). Plaintext assembled. AES-256-GCM encrypts moment + metadata (authenticated encryption). Ciphertext stored locally in Keychain (doubly encrypted: app layer + OS layer).

3
Sync → Remote Storage

Background sync detects encrypted moments. Encrypted payload sent to Supabase (server never decrypts). Unencrypted metadata (timestamp, tags, mood) stored separately for indexing/search. Server data is opaque.

4
Retrieval → Decryption on Device

User opens app. Master key retrieved from Keychain. Encrypted moments fetched from Supabase. AES-256-GCM decrypts locally in RAM only. Plaintext never persisted unencrypted on device.

5
Password Recovery → Key Rotation

User resets password via email verification. New Argon2id derives new master key. Old encrypted moments re-encrypted locally with new key. No server involvement. All key rotation on-device.

Design Exploration & Rejected Approaches

Metadata Encryption Strategy: Encrypting ALL metadata (tags, mood, timestamps) was considered for maximum privacy. Rejected in favor of split strategy: encrypted_content (ciphertext blob) + unencrypted metadata (timestamp, tags, mood). Rationale: unencrypted metadata enables server-side full-text search and indexing without decryption, drastically improving search performance. Risk of metadata exposure deemed acceptable given value of fast search.
Server-Side Encryption (pgcrypto): PostgreSQL native encryption (pgcrypto) was considered as additional server-side layer. Rejected: app now handles all encryption, server stores encrypted blobs opaque to itself. Cleaner architecture—server is dumb storage, client is security owner.
iCloud Backup Strategy Clarification: Manual iCloud backup toggle was initially considered (user opts in/out). Clarified: iCloud backup is automatic at OS level. If user restores on new device, encrypted moments sync automatically via Supabase (user signs in, fetches encrypted moments, decrypts locally with password-derived key). No additional user setup required. Automatic backup simplifies UX.
Biometric Unlock Deferral: Face ID / Touch ID unlock for master key retrieval was considered for Phase 2 MVP. Deferred to Phase 2+ optimization—adds complexity without blocking core security. MVP uses Keychain native security (device unlock required).

Locked Decisions

Encryption Standard: AES-256-GCM (authenticated symmetric encryption). Prevents ciphertext tampering; standard across industry.
Key Derivation: Argon2id (memory-hard, salt-based, GPU-resistant). Industry standard for password-to-key derivation post-2020.
Key Storage: iOS Keychain (OS-managed encryption, automatic on device lock). Master key never persisted in plaintext.
Server Role: Storage only. Server never has access to plaintext or master keys. Encrypted data is opaque at rest.
Metadata Strategy: Split encrypted_content (ciphertext) from unencrypted metadata (timestamp, tags, mood). Enables server-side search + indexing without decryption.
Decryption Scope: Decryption happens only on user's device, in RAM. Plaintext never persisted unencrypted locally or synced to server.
Password Recovery: Local key re-encryption via password reset. No master key reset; users retain all encrypted moments. Key rotation happens on-device post-reset.
Rich Context Integration: When pillar 3 (soaking) needs past moments for context synthesis, decrypt locally in-memory, pass plaintext to Gemini only in RAM (never persisted).
Encrypted Data Version Headers: Encrypted moment payloads include 1-2 byte algorithm version header (e.g., "AES-256-GCM v1"). Enables future algorithm upgrades without breaking decryption. Minimal overhead. Prevents silent failures if encryption standards change in phase 2+.

Tentative / TBD

Argon2id Parameters: Time cost, memory cost, parallelism locked on direction. Exact tuning depends on performance testing on actual iOS devices (iPhone 12 baseline).
Metadata Encryption: Should tags, mood, timestamps also be encrypted, or remain unencrypted for indexing? MVP keeps metadata unencrypted for search performance. Future: evaluate selective encryption.
Biometric Unlock: Face ID / Touch ID unlock for master key retrieval without password re-entry? Pillar 7 feature, not MVP. Deferred to phase 2+ optimization.
Account Deletion Policy: On account deletion, should encrypted moments be deleted immediately or retained in archive? Legal/compliance question, deferred to legal review.

Open Questions

  • Keychain Access Control: Should master key require device unlock? App-level PIN on top of Keychain? Evaluate threat model.
  • Backup & Restore: Should iCloud backup include encrypted moments? If user restores on new device, can they decrypt old moments with password?
  • Sync Conflict Resolution: If user edits moment offline then syncs, how do we merge encrypted versions? Lamport clock? Last-write-wins?
  • Argon2id Pod Selection: Which Argon2id Swift pod is most maintained + performant? Or should we implement via native C bindings?
  • Server-Side Indexing: Should we build full-text search on unencrypted metadata, or require client-side decryption for search?
  • Key Rotation Schedule: Should master key be rotated periodically (e.g., annually), or only on password reset?

Success Metrics (Phase 2 Beta)

  • Encryption Performance: <100ms to encrypt/decrypt moment on device (no user-perceptible lag)
  • Key Derivation Speed: <2s for Argon2id KDF on device (password reset must feel snappy)
  • Sync Success Rate: >99% encrypted moments sync without corruption
  • Zero Data Loss: 0 unencrypted user moments leak to server or local storage
  • Password Reset Completion: >95% users successfully reset password and retain encrypted moments
  • Keychain Reliability: 0 failures to retrieve master key from Keychain during normal app usage

Integration Points with Other Pillars

Pillar Integration
Pillar 0 (Onboarding) Password set during signup feeds into Argon2id KDF. Master key derived and stored in Keychain before first capture.
Pillar 1 (Capture) Moment auto-headline generated, then entire moment encrypted with AES-256-GCM before local storage. No plaintext persisted.
Pillar 3 (Soaking) Rich Context decrypts past 20 moments in-memory, passes plaintext to Gemini for context synthesis. Plaintext discarded after LLM processes.
Pillar 4 (Editing) User edits plaintext moment in-memory. Changes re-encrypted with AES-256-GCM. Updated ciphertext synced to server.
Pillar 5 (Search) Full-text search uses unencrypted metadata + server-side indexing. Rich content search (tags, mood) remains on encrypted payload; client decrypts + filters locally.
Pillar 6 (Menu Bar) Today/Entries tabs display plaintext moments after decryption on-device. Ciphertext never displayed to UI.
Pillar 7 (Notifications) Notification metadata (timestamp, category) unencrypted. Full moment content only shown in app after decryption.

Blocking Status & Next Steps

Pillar 2 is the blocking pillar for all downstream development. Pillar 3 (Soaking) cannot proceed until encryption architecture is locked and key rotation flow is validated.
