Formation Intelligence — API cost & capacity

Sept 2, 2026 — extends the July 5 cost doc, which only covers the old capture→reflection→prayer→journal loop and predates the Pillar 6 (Formation Intelligence) technical spec locked Sept 1
What's actually new here. Pillar 6's spec (PILLAR_6_FORMATION_INTELLIGENCE_TECHNICAL_SPEC.md) defines 3 LLM calls that don't exist in any prior cost analysis: Theme Detection (fires per journal), Narrative generation (fires on a correction, capped 1×/month/user), and Monthly reconciliation (fires 1×/month for a gated subset of users, and is the one place cost grows with how long someone's used the app — everything else in Dwelly's cost model so far is flat per-event forever).
These numbers are estimated, not measured. The July 5 doc's capture-loop numbers came from 4 live runs against real prompts. Theme Detection and the Dweller Profile Engine don't have prompts written or a model chosen yet — the spec explicitly punts model selection to "the shared LLM proxy (T-168)" without naming a provider. Everything below models plausible prompt sizes from the spec's own data shapes (Section 3 of the spec) and should be replaced with real measured numbers the first time these calls actually run.

1. The three new calls

Theme Detection (Row 3, Call B)

Fires once per journal, immediately after Journal Synthesis (Call A) succeeds. Reads the finished journal plus the user's current theme list; decides whether to reinforce an existing DetectedTheme or start a new one.

Frequency: exactly as often as journals get created — same event count already costed in the July 5 doc's capture loop. This call rides along on every one of those, it isn't a separate user action.

Narrative generation (Dweller Profile Engine)

Fires two ways: (a) immediately after a "Not quite" correction (Row 6, rate-limited to 1×/month/user), and (b) as part of monthly reconciliation (Row 7, below). Reads accumulated DetectedTheme records — not raw journals — plus the running summary, to regenerate narrativeText.

Frequency (correction path): capped at 1×/user/month by design (narrativeConfirmationUsedThisMonth) — and only for users who actually tap "Not quite," which should be a small minority. Cheap, flat, bounded.

Monthly reconciliation (Row 7) — the real cost driver

The spec is explicit that this is the one place cost grows with tenure: it rereads every journal and theme from ground truth, not just recent activity, for whichever users pass all three gate conditions (reflection tier + activity since last cycle + qualifying paid tier — that last one isn't defined yet, see Section 3 below).

Journal-count assumption: ~12/month is a placeholder (roughly 3/week) — no locked engagement-rate figure exists yet to replace it with. Output is the same ~250–400 tokens as any Narrative generation call regardless of input size.

This is a linear-growth cost, and it's gated but not capped. A reconciliation-eligible user active for 3 years with no drop-off could push a single monthly call past 100K input tokens. The gate (paid tier + activity + reflection tier) controls how many users hit this path, but nothing in the spec bounds an individual user's reconciliation cost as their history grows — worth deciding whether to cap "reread N most-recent journals" instead of "reread everything" before this ships, especially since Row 7's own write-up flags this as the metric to watch, not day-one cost.

That's the number worth watching, not the flat per-event costs.

3. What's blocking a precise number

Same three items the technical spec itself flags as open (Section 7 there), restated in cost terms:

Open itemWhy it matters for cost
Qualifying paid tier for Row 7's gate (spec 3.4, blocking)Directly controls what fraction of the user base ever hits the expensive reconciliation path. Without it, "how many users" in the table above is unknowable.
Model/provider choice for Formation Intelligence callsSpec says "shared LLM proxy (T-168)" only — doesn't name Gemini, GPT-4o mini, or otherwise. Pricing swings ~4x between Gemini's free tier and GPT-4o mini's paid rate (see July 5 doc's Round 1/2 tournament).
Precise "once a month" definition (spec item 4)Affects how tightly the correction-path cap actually bounds cost — a loose definition (e.g. resettable by toggling device clock) could let a user trigger more than 12 corrections/year in edge cases.

5. Bottom line

Formation Intelligence's two cheap, flat-cost calls (Theme Detection, correction-path Narrative generation) add a small, bounded amount to Dwelly's existing per-user cost — comfortably inside free-tier capacity even at meaningful scale. The one number worth tracking closely once this ships is monthly reconciliation cost per gated user, which grows every month they stay active and reconcile — unlike everything else in the app's cost model so far, this doesn't stay flat. The three blocking unknowns (paid-tier gate definition, model choice, "once a month" precision) all need answers before this can move from modeled estimate to the kind of measured, real number the July 5 doc has for the capture loop.
