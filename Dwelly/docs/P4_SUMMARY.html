Pillar 4: Journal Synthesis — Skeleton Summary

What We're Building

Pillar 4 (Journal Detail) is the single screen a synthesized journal lives in — reached either from the Entries list/calendar or directly from the "Open" pill Dwelly surfaces at the end of a capture loop. No separate raw-transcript tab, no confirmation screen, no prayer step in the loop (Prayer is Post-MVP, per Pillar 3's own status — not a Pillar-4-specific cut).

1
Capture Loop Completes

User finishes the conversational loop with Dwelly (Pillar 1). Dwelly's own closing message includes the journal preview inline in the same thread — no separate confirmation screen, no "want to pray about this?" prompt.

2
Journal Synthesis (Background)

LLM generates the journal entry from the conversation transcript the moment the loop ends — auto-generated title + 2-3 paragraph body + suggested moods. Runs in the background; the inline preview card and "Open" pill are ready as soon as synthesis completes.

3
Open → Journal Detail

Tapping "Open" (from the inline card right after capture, or from an entry in the Entries list/calendar later) goes directly to the single Journal Detail screen. One view — no Entry/Dwelling Place split.

4
Editing & Customization

User can: select/modify mood tags from predefined list, add a photo of their experience (camera or library), edit journal text. Delete capability included. Re-engagement: can add reflections to old entries (encourages re-capture for new moments).

4b
Pending / Not-Yet-Synthesized State (updated Aug 27, 2026)

The journal entry is created immediately and shows up in the Entries list right away, in a pending state — not withheld until synthesis finishes. This covers every reason synthesis hasn't completed yet: offline, LLM provider outage/rate-limit, or the app's own API budget exhausted — one rule, no special-casing. The screen shows a soft "Processing your journal..." state (raw transcript visible only as a temporary placeholder, never presented as the finished artifact) and swaps in the synthesized version silently once it's ready. No permanent raw-transcript fallback, ever. Updated Aug 27, 2026 — there is no manual "Retry" tap anywhere in Pending. Retries happen silently and indefinitely in the background instead; the user never sees a retry affordance or a failure state to act on. A "your journal is ready" push notification on completion is a good future hook — deferred to Pillar 9 (Notifications), not built here.

Pending badge/flame treatment (locked Aug 27, 2026): the pending indicator uses the real Dwelly flame asset (not a generic spinner or icon), rendered as a small dot + text pattern (flame dot + "Still working on this" style label), with two-line reassurance copy underneath so the state reads as calm/in-progress rather than broken or stalled.

Design Exploration & Rejected Approaches

SUPERSEDED this session — Single Journal Detail view, not a two-tab architecture: The Entry + Dwelling Place split is cut. There is one Journal Detail screen. It's reached from the Entries list/calendar or directly via "Open" after a capture loop. Raw transcript is not a permanent, separately-tabbed artifact — it only ever appears as a temporary placeholder during the pending state (Flow 4b), swapped out once synthesis completes.
SUPERSEDED this session — No confirmation screen, no prayer step in the loop: Prayer is Post-MVP (Pillar 3's own status). The loop is Capture → Dwelly's closing message with the journal card inline → Open → Journal Detail. No intermediate confirmation screen asking to pray.
Moods/Tags Unified: Single predefined palette (emotional + spiritual moods: Reflective, Conflicted, Exhausted, Hopeful, Loved, Prayerful, etc.). Rejected: separate moods (emotional) vs tags (topical). For spiritual journaling, emotional state IS the spiritual mood—keeping them unified reduces mental overhead and keeps interface simpler.
LLM Synthesis Over User-Written Journals: App generates journal from conversation rather than asking user to write journal manually. Rationale: conversation is already deeply reflective; synthesis reframes it as journal. User can edit post-synthesis. Rejected: requiring user to write (adds friction, creates blank-page anxiety, duplicates reflection work). Rejected: only showing conversation (lacks contemplative synthesis/reframing).
Post-Synthesis Photo Upload (v1): User can add/remove photos after journal is created. v2 will add GAI (Generative AI image descriptions) for photos. Rejected: requiring photo at capture time (not all moments are visual). Rejected: no post-synthesis photo editing (limits flexibility).

Encryption: Server-Side AES-256-GCM (matches Pillar 2's actual current model), corrected this session: Journal body + transcript encrypted at rest with a server-managed key, transiently decrypted only for legitimate processing (e.g. synthesis) — not the zero-knowledge/full-E2E model this doc previously described. Transcript not searchable server-side (client-side search only). Offline-capable at the capture layer.
Journal Editability (Detail View Only): Users edit journal in detail view (not on list cards). Can modify moods/tags, add/remove photos, edit journal text post-synthesis. Edit tracking enabled (note if user has modified journal).
Delete Capability: Users can delete journal entries (soft delete supported). Encourages re-capture if they want to refresh/re-engage.

Re-engagement: Users can add reflections to old journal entries. Re-prayer deferred to backlog (encourages fresh capture instead). Fresh captures create new journal entries (preferred over modifying old entries).
LLM Synthesis Output: Title (auto-generated, 4-6 words) + Body (2-3 paragraph narrative prose, not structured sections) + Suggested Moods (2-3 tags, user can override). Tone: contemplative, personal, affirming. Mirrors user's language but reframes as spiritual reflection.
Moods/Tags: Predefined Palette: User-selectable from spiritual/emotional palette (Reflective, Conflicted, Exhausted, Hopeful, Loved, Prayerful, Grieving, Grateful, etc.). Limit 2-3 per journal. Searchable across library.
Photo Management v1: User can add photos via camera or photo library after journal synthesis. Can remove photos. v2 will add GAI descriptions. No photo required for synthesis (text-only moments are valid).
UPDATED Aug 27, 2026 — Pending State replaces the permanent transcript fallback, and now has no manual Retry either: The July 9 version of this decision let the raw transcript become the permanent journal body after failed retries, with an "accept as-is" option. That's gone. Now: any reason synthesis hasn't completed (offline, LLM provider outage, exhausted API budget) puts the entry in status: "pending" — same state, same soft "Processing your journal..." treatment, no special-casing per cause. Raw transcript shows only as a temporary placeholder while pending, never as an accepted permanent artifact. Retries happen silently and indefinitely in the background — there is no manual "Retry" affordance anywhere in Pending, and no ceiling where the app gives up and surfaces a failure state. No reflection is ever lost; it's just never presented as "finished" until it actually is. Fallback/placeholder transcript is encrypted the same as the synthesized body (AES-256-GCM).
LOCKED Aug 27, 2026 — T-159 resolved: two-mechanism background retry for Pending entries. Since there's no manual Retry, Pending entries need a real background path to eventually complete, confirmed by Kell as: (1) Periodic background sweep (primary) — BGTaskScheduler (BGAppRefreshTask) periodically wakes the app and retries synthesis for every pending entry, with backoff between attempts per entry. Runs even if the user never opens the app. Caveat: this isn't on a fixed clock — iOS decides actual fire timing based on usage patterns and battery state, so "periodic" means "iOS's discretion," not a guaranteed interval. (2) Piggyback on new-capture sync (fallback) — whenever SyncManager runs a sync for a newly-created moment, it also sweeps and retries any other pending entries in the same pass. Not because entries are related to each other synthesis-wise (they're independent LLM calls against independent transcripts — one entry completing has no effect on another), but because a sync-triggering event is a convenient, frequent hook to also attempt pending retries, likely faster in practice than waiting on the OS-scheduled sweep for an actively-journaling user. Together: mechanism (1) is the guarantee, mechanism (2) is the fast path.
